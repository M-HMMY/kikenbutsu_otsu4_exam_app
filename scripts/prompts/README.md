# 章を書かせるときのプロンプト

教本の各章は、ここに置いたプロンプトを Codex CLI に渡して書かせます。

## いまの状態

**4 本とも、中身は 1 つ前のアプリ（生成AIパスポート試験）のままです。**骨組みを見本として持ってきただけなので、**そのまま渡さないでください。**各ファイルの冒頭に警告を入れてあります。

| ファイル | 用途 | 状態 |
| --- | --- | --- |
| [00-common.md](00-common.md) | 全章に共通する決まりごと。読者像・記法・節の骨格・リンクしてよい節 ID の全一覧・報告の形 | **要書き換え** |
| [20-questions.md](20-questions.md) | 確認問題を書かせる | **要書き換え** |
| [90-review.md](90-review.md) | 教本の通しレビュー（ひな形） | **要書き換え** |
| [91-review-questions.md](91-review-questions.md) | 確認問題の通しレビュー（ひな形） | **要書き換え** |

章ごとの執筆プロンプト（`02-…` 以降）は**まだ 1 本もありません。**章立てが確定してから作ります。

**`01-intro.md` は作りません。**入門編（`src/data/textbook/intro.ts`）は、他章のリンク先（用語辞典・計算の読み方）と**文体の見本**を兼ねるので、依頼する側が手で書きます。章のプロンプトはそれを見本として読ませます。

## 使い方

```bash
codex exec --cd "C:/Dev/otsu4_exam_app" --sandbox workspace-write --color never \
  -o out-02.txt - < scripts/prompts/02-xxx.md
```

- `--sandbox workspace-write` … このリポジトリの中だけ書き換えを許す
- `-o out-02.txt` … **最終メッセージだけ**をファイルに落とす。途中の思考ログを読まずに済むので、依頼した側のコンテキストを食わない
- `-` … プロンプトを標準入力から読む（長い日本語をシェルの引用符で壊さないため）

複数を同時に走らせられます。**ただし 1 ファイル 1 担当**にしてください。`src/data/textbook/<章 ID>.ts` と `src/data/questions/<章 ID>.ts` を 1 章 1 ファイルにするのはこのためです。

**レビューは `--sandbox read-only` で走らせます。**指摘だけさせて、直すのは依頼した側。書き換えまで任せると、何が変わったのか追えなくなります。

## プロンプトに入れてあること（省くと品質が落ちます）

系譜 5 本で実際に効いた要素です。**書き換えるときは、この 14 項目を上から順に潰してください。**

1. **読むファイルの指定** … `CLAUDE.md`、`00-common.md`、出題範囲の資料、`src/data/textbook/intro.ts`（文体の見本）
2. **書くファイルの限定** … 「他のファイルは絶対に変更しないでください」
3. **節の一覧を表で渡す** … id・タイトル・ねらい・分数・扱う内容。**id を決めて渡さないと勝手な id を作ります**
4. **読者像** … 一文で言い切り、通じる語と通じない語を具体例で書く
5. **この試験に出ない形を禁じる** … 姉妹アプリでは「数式を書かせない」がこれでした（下の「このアプリ固有の注意」を参照）
6. **用語の扱いの型** … 姉妹アプリでは「英略語は初出で正式名称・訳・何をするものかの 3 点セット」
7. **時点の明記を求める** … 改正・改訂があるものは「いつ時点の話か」を本文に書かせる
8. **章の背骨** … その章を貫く一本の考え方。用語がバラバラに見えなくなります
9. **節の骨格** … ざっくり言うと → 本論 → まとめ → quiz。`digest.ts` が拾う書式
10. **一問一答の数の下限** … 用語の取り違えで落とす試験ほど効きます
11. **記法の注意** … バックスラッシュのエスケープ、ヒアドキュメント禁止、**`compare` は「1 行 1 セル」で `::` は左右の区切りではない**、図の中で `**` は効かない
12. **リンクしてよい節 id の全列挙** … 省くと存在しない節へリンクして検査に落ちます
13. **間違えやすい事実の名指し** … 先回りで釘を刺す。**姉妹アプリでは、名指しした箇所は全章で正しく書けていました**
14. **`npm run check` を実行させない** … 並行実行だとキャッシュが衝突する。検査は依頼した側がまとめて 1 回

## このアプリ固有の注意（書き換えるとき必ず入れる）

姉妹アプリの注意（数式を出さない・英略語の 3 点セット）は**この試験には当てはまりません。**代わりに入れるべきものが 4 つあります。

1. **数字をごまかさせない。** 指定数量、引火点、発火点、燃焼範囲、保有空地の幅、タンクの容量。**この試験は数字そのものを問います。**一次資料（消防法・政令・規則）の値を確認させ、「およそ」で逃げさせないこと
2. **計算問題を出させる。** 「基礎的な物理学及び基礎的な化学」には計算が出ます。**姉妹アプリはここが空でした。**比熱・熱量・熱膨張・濃度あたりは `src/data/drills.ts` で自動生成する側に回すことも検討してください
3. **法令の条番号を書かせるなら、必ず確認させる。** 系譜で繰り返し出ているのが「条文の要件の書き落とし」です。**引用するなら要件を全部並べる**こと
4. **3 科目それぞれで 6 割という基準を、どの章でも前提にする。** 「法令は捨てて物化で稼ぐ」という戦略が成り立たない試験です。読者がそう誤解する書き方をさせないこと

## Codex の利用上限に注意

姉妹アプリでは、5 本を並行で走らせたとき、3 本が**編集を終えた直後・報告を書く前**に利用上限に当たりました。ファイルは書き換わっているのに `-o` の出力が空、という状態になります。

- **`-o` の出力が空でも、ファイルは変わっていることがある。**`git diff` で必ず確かめる
- **何が済んで何が残ったかは、こちらで検算する。**指示した用語を `grep -c` で数えるのが速いです
- **同時に走らせるのは 4 本まで**にしておくのが無難です

## 報告を鵜呑みにしないこと

Codex は毎回「事実に自信がない箇所はありません」と報告してきますが、**そのまま信用してはいけません。**（そのため 90 番・91 番のレビュープロンプトでは、この報告を明示的に禁じてあります。）

- 機械的な検査は `npm run check` で必ず確認する
- 内容の正しさは、**書いた人とは別の目**で通しレビューする。省略できる工程ではありません（根拠は [../../docs/handover.md](../../docs/handover.md) の §4）
- **直したら、直した版をもう一度見せる。**姉妹アプリでは、1 巡目の指摘を反映して書き直した版に 2 巡目を掛けたら、**書き直したところから「誤答が実は正しい」が 3 件**出ました
